# 配置与常量管理规范

本文档旨在为 Project Tracker 的配置项与常量管理提供基础指导原则。合理的配置与常量管理能够避免代码中散落“魔法值”，确保应用行为的可预测性与可维护性。

---

## 一、 核心定义与区分

在编写代码前，必须明确区分“配置”与“常量”：

1. **配置 (Configuration)**：
   - **定义**：在应用运行期间可能发生变化，或者需要根据不同环境/用户进行定制的参数。
   - **特征**：通常由用户设置、环境变量或外部文件提供。
   - **示例**：API 端点、AI 模型名称、默认导图深度、主题模式、数据存储路径。

2. **常量 (Constants)**：
   - **定义**：在应用生命周期内绝对固定、不会改变的硬编码值。
   - **特征**：用于消除代码中的“魔法数字”或“魔法字符串”，提升可读性。
   - **示例**：最大重试次数、防抖延迟时间（如 500ms）、默认分页大小、固定的错误码前缀。

---

## 二、 存放位置规范

根据技术栈（React + Tauri + Rust），配置与常量必须存放在指定的物理位置，严禁在业务逻辑中直接硬编码。

### 2.1 前端 (React / TypeScript)

- **环境变量**：存放在项目根目录的 `.env` 文件中（仅限开发期，不提交到 Git）。
- **运行时配置**：通过 Zustand Store (`src/store/useAppStore.ts`) 管理，并与后端的 `app-state.json` 保持同步。
- **UI/业务常量**：存放在 `src/lib/constants.ts` 或相关组件的同级目录下（如 `src/components/ChatPanel/constants.ts`）。
- **类型定义**：配置项的 TypeScript 接口必须定义在 `src/types/` 目录下。

### 2.2 后端 (Rust)

- **环境变量解析**：在应用启动时（`main.rs` 或专门的 `config.rs`）读取 `.env`，并注入到全局状态或传递给 Service 层。
- **硬编码默认值**：存放在 `src-tauri/src/models/` 或 `src-tauri/src/services/` 的顶部，使用 `const` 或 `lazy_static` 声明。
- **持久化配置**：由 `tauri-plugin-store` 管理的 `app-state.json`，以及用户数据目录下的 `prompts.json`。

---

## 三、 优先级与加载机制

当同一个配置项在多个地方存在定义时，必须遵循严格的优先级覆盖规则（自上而下，高优先级覆盖低优先级）：

1. **用户运行时设置 (最高)**：用户在设置页修改并保存的值（Zustand Store / `app-state.json`）。
2. **项目级配置**：特定项目目录下的配置文件（如 `.project-tracker/prompt.json`）。
3. **环境变量**：开发环境下的 `.env` 文件或系统环境变量。
4. **框架/系统默认值**：Tauri 配置文件 (`tauri.conf.json`) 中的默认设置。
5. **代码级硬编码默认值 (最低)**：Rust 或 TypeScript 代码中定义的兜底常量（如 `DEFAULT_MODEL = "gpt-4o"`）。

**原则**：任何配置项都必须有至少一个“兜底默认值”，确保在极端情况下（如配置文件损坏、环境变量缺失）应用仍能正常启动和运行。

## 四、 命名与格式规范

1. **常量命名**：
   - 必须使用 **SCREAMING_SNAKE_CASE**（全大写，下划线分隔）。
   - 示例：`MAX_SCAN_DEPTH`、`DEBOUNCE_DELAY_MS`、`DEFAULT_AI_ENDPOINT`。

2. **配置键名 (Key)**：
   - 在 JSON 或 Store 中，使用 **camelCase**（小驼峰）保持一致性。
   - 示例：`apiEndpoint`、`defaultMapDepth`、`isDarkMode`。

3. **分组与注释**：
   - 相关的常量必须逻辑分组，并添加简短的注释说明其用途和取值范围。
   - 示例：
     ```typescript
     // AI 对话相关常量
     const AI_CHAT_MAX_TOKENS = 4096;
     const AI_CHAT_TIMEOUT_MS = 30000;
     ```

---

## 五、 敏感配置处理

涉及密钥、密码、Token 等敏感配置时，必须遵循以下红线原则：

1. **严禁硬编码**：绝对不允许将 API Key、密码等明文写在源代码中。
2. **环境变量隔离**：开发期的敏感信息必须放在 `.env` 中，且 `.env` 必须被 `.gitignore` 严格排除。
3. **落盘加密**：用户保存的敏感配置（如 API Key）在写入磁盘前，必须经过加密处理（如项目现有的 AES-256-GCM 方案）。
4. **日志脱敏**：在打印日志或上报错误时，敏感配置项必须被掩码处理（如只显示前 4 位和后 4 位，或仅记录长度）。

---

## 六、 验证 Checklist

在新增或修改配置/常量时，请确认：
- [ ] 代码中不存在未经定义的“魔法数字”或“魔法字符串”。
- [ ] 新增的配置项已在所有优先级层级中定义了合理的默认值。
- [ ] 敏感配置没有以明文形式出现在代码或日志中。
- [ ] 常量的命名符合 SCREAMING_SNAKE_CASE 规范。
