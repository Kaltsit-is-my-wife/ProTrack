# 前端代码规范与架构原则 (Project Tracker)

本文档为 Project Tracker 前端开发的核心指导原则，旨在确保代码的专业性、可维护性与高可靠性。所有后续开发、重构及 Agent 辅助生成代码时，均需严格遵循本规范。

---

## 一、 核心设计理念

1. **UI 与逻辑彻底分离**：React 组件只负责渲染和用户交互，业务逻辑、数据处理、副作用必须抽离到 Hooks 或 Lib 中。
2. **类型驱动开发**：TypeScript 严格模式是底线，类型定义优先于实现，拒绝任何运行时类型猜测。
3. **组合优于继承**：通过小组件组合构建复杂界面，避免创建庞大且难以维护的“上帝组件”。

---

## 二、 目录结构与模块职责

严格的物理隔离是保证逻辑清晰的前提。

- **`components/` (UI 层)**：仅包含 React 组件。负责 JSX 渲染、事件绑定和局部 UI 状态。禁止包含复杂的业务计算或数据请求逻辑。
- **`hooks/` (逻辑层)**：封装与 DOM、浏览器 API 或复杂副作用相关的自定义 Hooks。作为组件与底层逻辑的桥梁。
- **`lib/` (工具层)**：纯函数库。包含数据处理、算法（如 ELK 布局计算）、API 请求封装。不依赖 React 生命周期，易于独立测试。
- **`store/` (状态层)**：Zustand 全局状态。仅存储跨组件共享的核心业务数据，禁止存储纯 UI 状态（如弹窗开关）。
- **`types/` (类型层)**：全局共享的 TypeScript 接口和类型定义。

---

## 三、 组件设计原则

1. **单一职责**：一个组件只解决一个问题。如果一个组件承担了布局、数据获取、状态管理等多种职责，必须拆分。
2. **文件规模控制**：单个组件文件（含样式和逻辑）应控制在合理范围内（建议 300 行以内）。超过阈值必须提取子组件或抽离 Hooks。
3. **Props 最小化**：只传递组件真正需要的 Props。避免“Props 钻取”（多层透传），深层依赖应通过 Zustand 或 Context 解决。
4. **受控与非受控明确**：表单类组件需明确设计为受控（由父组件管理 value）或非受控（内部管理 value），避免状态冲突。

---

## 四、 状态管理原则 (Zustand)

1. **全局与局部的边界**：
   - **局部状态 (`useState`)**：仅在当前组件内使用的 UI 状态（如输入框内容、下拉菜单展开状态、Loading 动画）。
   - **全局状态 (`useAppStore`)**：跨组件共享的业务数据（如当前选中的项目 ID、全局设置、项目列表）。
2. **拒绝状态冗余**：如果一个状态可以通过其他状态计算得出（派生状态），不要存入 Store，而是在组件内使用 `useMemo` 实时计算。
3. **细粒度订阅**：在组件中使用 Store 时，必须使用 Selector 函数精确选取所需字段，避免无关状态变更导致整个组件重渲染。

---

## 五、 样式与 UI 规范 (Tailwind CSS + shadcn/ui)

1. **原子类优先**：所有样式优先使用 Tailwind CSS 原子类组合。禁止在组件内编写大段自定义 CSS，仅在极端复杂动画或特定布局时使用 CSS 模块。
2. **组件库复用**：优先使用 shadcn/ui 提供的基础组件。如需定制，通过 Props 或 Tailwind 类名覆盖，禁止直接修改 shadcn 源码。
3. **主题一致性**：严格遵循设计系统的颜色、间距和圆角变量。暗色模式适配必须使用 CSS 变量或 Tailwind 的 `dark:` 修饰符，禁止硬编码颜色值。

---

## 六、 类型安全与错误处理

1. **零妥协的类型检查**：
   - 严禁使用 `any` 类型。
   - 严禁使用 `@ts-ignore` 或 `@ts-expect-error` 掩盖类型错误。
   - 严禁使用 `as unknown as Type` 进行不安全的类型断言，除非有充分的运行时校验。
2. **结构化错误反馈**：
   - 所有后端交互必须通过统一的封装函数调用。
   - 错误必须被捕获并转化为用户可理解的提示（Toast），严禁静默吞掉错误或仅输出到控制台。
   - 区分“用户可修复错误”与“系统异常”，提供明确的引导。

---

## 七、 性能与渲染控制

1. **避免不必要的重渲染**：
   - 对于接收复杂对象或函数的子组件，合理使用 `React.memo`。
   - 在事件处理函数和依赖项中，正确使用 `useCallback` 和 `useMemo` 保持引用稳定性。
2. **长列表与图渲染优化**：
   - 针对 React Flow 等重渲染组件，必须利用其内置的虚拟化或节点状态管理机制，避免全量更新。
   - 复杂计算（如目录树遍历、布局算法）必须放在 Web Worker 或 useMemo 中，阻塞主线程。

---

## 八、 Tauri IPC 交互原则

1. **统一封装**：前端禁止直接裸调用 Tauri 的 `invoke`。必须通过封装好的安全调用函数进行交互，以统一处理错误、加载状态和类型转换。
2. **异步体验**：所有 IPC 调用均为异步操作。必须提供明确的加载反馈（如 Spinner、骨架屏或按钮禁用状态），防止用户重复触发。
3. **数据校验**：后端返回的数据在前端使用时，应假设其结构可能不符合预期（防御性编程），必要时进行运行时校验或提供安全的默认值。
